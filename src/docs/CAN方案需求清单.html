按 1.5mA 待机算，7Ah 电瓶理论上能撑约 190 天。但电瓶自放电和车上原有暗电流也在耗，实际留足余量按 1–2 个月评估。这个数字足以支撑"先按 16 脚取电"的选择。

深睡的两种唤醒方式

方式唤醒延迟实现难度说明
定时唤醒
推荐		 最长 5 分钟 低 每 5 分钟醒 2 秒，检查总线上有没有帧；有就留在运行态，没有就继续睡。平均电流增加约 0.8mA。不用改硬件，纯固件。
CAN 活动唤醒 几乎即时 中 把收发器的 RXD 接到支持 GPIO 唤醒的引脚，总线一有跳变就醒。问题是收发器待机时也要供电，静态电流压不下去，实际比定时唤醒更费电。
一个容易忽略的细节

钥匙拧到 ON 但没启动时，ECU 通常已经在总线上发帧了——所以定时唤醒能正常工作。但如果 ECU 在熄火后完全不发帧，总线上一个字节都没有，任何"看总线活动"的判断都会超时。这是正常的，超时就继续睡，不要当成故障。

两个必须注意的地方

不要同时插 USB 和 12V。开发板 USB 供电和 5V 脚之间多数只有一只肖特基二极管，倒灌风险取决于具体板子。调试时拔掉 12V，或者干脆调试阶段只用 USB 供电（此时不需要降压模块）。

改动前断开电瓶负极。OBD 的 16 脚是常电，插头插着的时候整条线都是活的，剪线钳一碰车架就是短路。

五、软件栈

发送端（ESP32-S3 N16R8）

框架 ESP-IDF 5.5，纯 C，无 RTOS 之外的高级框架。按职责拆成七个模块：

模块职责要点
can_linkTWAI 初始化与错误恢复500 kbps，11-bit ID，只收 0x7E8–0x7EF。必须实现 bus-off 自动恢复，否则一次干扰就永久静默
isotpISO 15765-2 拆包单帧（SF）必做；多帧（FF + CF 流控）也要做——读 VIN 或一次性请求多个 PID 时会用到
obd_pollPID 轮询调度按频率分档：快项 10Hz、慢项 1–2Hz。请求间隔 20–50ms，太快 ECU 会丢帧
decodePID 公式解码查表实现，见第六节
filter数值平滑转速用中值滤波去尖峰，水温用 EMA 慢跟踪
odo里程与清码补偿消费 PID 0x31；检测回落并把差额记进 offset，保证显示值单调不减；每 1 km 写一次 NVS
runtime运行时长计时仅在总线活跃（ECU 上电）时累加；每 30 分钟写一次 NVS，掉电最多丢 30 分钟
uplinkESP-NOW 打包发送广播地址，无需配对；20Hz 上限，实际 10Hz 够用
power睡眠管理无总线活动 60s 进深睡；定时 5 分钟唤醒探测

接收端（圆屏 1.75C）

模块职责要点
espnow_rx收包与校验丢包用 seq 判断；连续 2s 无包在界面打"信号丢失"
uiLVGL 9 界面转速圆弧 30fps，数字 5Hz 局部刷新。刷新缓冲约 40 行 ≈37KB 放内部 RAM
storageNVS 读写存里程基数、亮度、主题
power亮度与防烧屏静止 5 分钟降亮度；静止 30 分钟熄屏；长时间静止做像素偏移

圆屏的驱动用微雪官方托管组件 esp32_s3_touch_amoled_1_75c，不要自己写 CO5300 的 QSPI 初始化——那个时序很折磨人。

无线协议

ESP-NOW 单包载荷上限 250 字节，这个结构体 23 字节，足够。注意是 v2：车速已移除，换为运行分钟数，接收端必须同步：

// 发送端与接收端共用的头文件 common/telemetry.h
typedef struct __attribute__((packed)) {
    uint16_t rpm;        // 发动机转速，0–12000
    int8_t   coolant;    // 水温 °C，-40–125
    int8_t   intake;     // 进气温度 °C
    uint8_t  tps;        // 节气门开度 %
    uint8_t  fuel;       // 油量 %，不支持时置 0xFF
    uint16_t volt_dv;    // 系统电压，单位 0.1V
    uint16_t run_min;    // 发动机累计运行分钟，饱和 65535
    uint32_t odo_dam;    // 里程，单位 0.1km（源 = PID 0x31，已做清码补偿）
    uint16_t flags;      // TF_RPM / TF_COOLANT / ... / TF_ODO
    uint32_t seq;        // 递增序号，用于丢包判断
} telemetry_t;

flags 是必须的：某项读不到时接收端要显示 -- 而不是显示 0，否则骑手会以为是真实数据。

关于里程：0x31 救回来了

标准 OBD-II 确实没有「总里程」PID，但有一个 0x31「Distance traveled since codes cleared」——本车实测返回 11582 km，与表显里程同一量级。只要不清故障码，它就等于里程，对保养提醒完全够用。

唯一的坑：清码会归零。直接透传的话，某天清了码里程就从 11582 跳成 1，比不显示更糟。固件里用 offset 补偿：检测到显著回落（> 50 km）时把差额记进 NVS，显示值继续单调上升。

降级路径：若 0x31 不被支持，改试非标准 0xA6；两者都不行就置位不显示，界面显示 --。

轮询时序

// 请求：功能寻址，所有 ECU 都听
TX  ID=0x7DF  DLC=8  02 01 0C 00 00 00 00 00
// 响应：发动机 ECU
RX  ID=0x7E8  DLC=8  04 41 0C 1A F8 00 00 00
// RPM = 0x1AF8 / 4 = 1726

// 如果功能寻址没人应答，改物理寻址（发动机 ECU）
TX  ID=0x7E0  DLC=8  02 01 0D 00 00 00 00 00
RX  ID=0x7E8  DLC=8  03 41 0D 3C 00 00 00 00
// 车速 = 0x3C = 60 km/h

九、待确认项与风险

项目影响怎么确认 / 怎么兜底
协议是否 ISO 15765-4 / 500k已确认ELM327 + Car Scanner 实测：ISO 15765-4 CAN (11 bit ID, 500 kbaud)，ECU 名 ECM-EngineControl，握手正常。本清单直接适用
功能寻址是否被响应中很多 ECU 忽略 0x7DF，只答物理地址 0x7E0。固件里做成超时自动切换，不要写死
车速 PID 是否有效已排除实测 01 0D 无响应。转前轮仪表动、手机不动 → 轮速信号直连仪表。项目不再处理车速，也不做轮速旁路
前置 USB 口电流中确认是 5V/1A 以上。圆屏峰值约 0.5A，若同时充手机可能不够
前置 USB 是否 ACC 断电低熄火后断电最理想。若是常电，圆屏会一直亮，需要固件里做无数据熄屏
震动导致焊点开裂中USB 座热熔胶固定、排针改焊接、模块灌 704 胶、线束留应力环
总线错误 / 干扰中TWAI 开 bus-off 自动恢复；12V 进线套磁环；CANH/CANL 全程双绞
一句话总结

硬件只有 5 颗器件 + 一根插头线，软件是 两个 ESP-IDF 工程 + 一个共享头文件。真正的难点不在代码量，而在协议确认和供电可靠性这两件事上——这两件做对了，剩下的是按部就班。
